# المنيب جو — almoneib-go

خدمة توصيل محلية (المنيب — مصر). Next.js 15 (App Router) + Supabase (Postgres/Auth/RLS) + Cloudinary + Vercel.

---

## 1. الإعداد الأولي

### أ) Supabase
1. أنشئ مشروع جديد على [supabase.com](https://supabase.com).
2. من **SQL Editor**، شغّل كل ملفات `supabase/migrations/` **بترتيبها الرقمي** (0001 → 0046) — أو استخدم `supabase db push` عبر الـ CLI بعد `supabase link`.
   > لو كنت طبّقت المشروع قبل كده لحد 0021: يكفي تشغّل ملف `0022_fix_agent_profiles_insert_policy.sql` بس (الجديد) فوق قاعدة البيانات الحالية.
   > لو كنت طبّقت لحد 0022: شغّل كمان `0023_popular_products_for_customers.sql` (قسم "منتجات ناس كتير طلبتها" في الصفحة الرئيسية).
   > لو كنت طبّقت لحد 0023: شغّل كمان `0024_decline_shopping_assignment.sql` و`0025_online_payment_proof.sql` (رفض المندوب بسبب + نظام الدفع الأونلاين).
   > لو كنت طبّقت لحد 0025: شغّل كمان `0026_banner_and_announcement_settings.sql` (إعدادات البانر وشريط الإعلانات).
   > لو كنت طبّقت لحد 0026: شغّل بالترتيب `0027` حتى `0030` (الخصومات، العروض، أكثر العملاء طلبًا، وربط إشعارات Push بكل الأحداث المهمة).
3. من **Authentication → Providers**، تأكد أن Email/Password مفعّل (نستخدمه بدلاً من Phone Auth لتفادي تكلفة SMS — راجع القسم 3 أدناه).
4. انسخ `Project URL` و`anon key` و`service_role key` من **Settings → API**.

### ب) Cloudinary
أنشئ حسابًا مجانيًا على [cloudinary.com](https://cloudinary.com)، وانسخ Cloud Name وAPI Key وAPI Secret.

### ج) متغيرات البيئة
انسخ `.env.example` إلى `.env.local` واملأ القيم:
```
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_ANON_KEY=
SUPABASE_SERVICE_ROLE_KEY=
NEXT_PUBLIC_VAPID_PUBLIC_KEY=
VAPID_PRIVATE_KEY=
NEXT_PUBLIC_CLOUDINARY_CLOUD_NAME=
CLOUDINARY_API_KEY=
CLOUDINARY_API_SECRET=
```
لتوليد مفاتيح VAPID (لإشعارات Push المجانية):
```bash
npx web-push generate-vapid-keys
```

### د) التشغيل محليًا
```bash
npm install
npm run dev
```
افتح http://localhost:3000

### هـ) النشر
```bash
vercel
```
وأضف نفس متغيرات البيئة في إعدادات المشروع على Vercel.

## 2. إنشاء أول Super Admin (خطوة يدوية إلزامية مرة واحدة)

أي تسجيل جديد عبر شاشة `/register` يُنشأ تلقائيًا بدور `customer` فقط (لأسباب أمنية — لا يمكن لأي شخص منح نفسه صلاحيات إدارية). لإنشاء أول Super Admin:

1. سجّل حسابًا عاديًا من `/register` برقم هاتفك.
2. من **SQL Editor** في Supabase، نفّذ:
   ```sql
   update public.users set role = 'super_admin' where phone = '01xxxxxxxxx';
   ```
3. سجّل الخروج والدخول مرة أخرى — ستنتقل تلقائيًا للوحة التحكم.

من هذه النقطة، يمكن لهذا الـ Super Admin إنشاء حسابات Business Admin وDelivery Agent بنفس الطريقة (تسجيل عادي ثم تغيير `role` من SQL Editor أو ببناء شاشة "إدارة المستخدمين" لاحقًا — لم تُبنَ بعد، راجع قسم "المتبقي" أدناه).

## 3. قرارات تصميم مهمة يجب معرفتها

- **لا يوجد Phone OTP**: التسجيل/الدخول يستخدم بريدًا داخليًا وهميًا مبنيًا من رقم الهاتف (`01xxxxxxxxx@otlobha.local`) مع Supabase Auth القياسي (بريد/كلمة مرور). رقم الهاتف الحقيقي محفوظ ومُتحقق من صيغته في `public.users.phone` وهو المستخدم في كل الشاشات والرسائل — العميل لا يرى هذا البريد الوهمي إطلاقًا.
- **لا يوجد WhatsApp API مدفوع**: كل الرسائل تُبنى تلقائيًا (نص جاهز من `whatsapp_templates`) لكن يُرسلها المندوب/الإداري يدويًا بضغطة زر واحدة تفتح رابط `wa.me` مع النص جاهزًا. لا إرسال آلي فعلي.
- **استرجاع كلمة المرور**: بنفس آلية واتساب اليدوي أعلاه — لا SMS ولا تكلفة.
- **الأسعار/العمولة/مديونية الإلغاء تبدأ من صفر** كما اتُفق، وتُضبط من `/admin/settings`.
- **لا تعديل مباشر على `orders.status`**: كل انتقال حالة يمر حصرًا عبر دوال RPC (`accept_order`, `approve_invoice`, `mark_delivered`...) لضمان الـ State Machine ولمنع أي قفزة حالة غير مشروعة.
- **كل عملية مالية/حساسة تُسجَّل تلقائيًا في `audit_log`** داخل نفس الـ Transaction — لا يمكن نجاح العملية دون تسجيلها.

## 5. ما تم بناؤه بالكامل ✅

- قاعدة البيانات كاملة (29 جدولًا) + RLS صارمة على كل جدول.
- دورة حياة الطلب الكاملة (State Machine) عبر دوال RPC آمنة.
- التعيين الذكي للمندوب (تفضيل نفس المندوب السابق، ثم الأقل حملاً).
- تطبيق العميل كاملاً: تصفح، سلة، طلب يدوي، دفع عند الاستلام، تتبع، فاتورة، ديون، تقييم، شكاوى.
- تطبيق المندوب كاملاً: تسجيل الشراء، تجهيز الفاتورة، التوصيل، تأكيد الاستلام (لا تسليم بدون تأكيد الدفع)، النقل بين المندوبين.
- لوحة الإدارة: الطلبات (قبول/رفض/اعتماد فاتورة/إلغاء)، العملاء (حظر)، المنتجات (إضافة/تعديل السعر/تفعيل وتعطيل)، التصنيفات (إضافة/تفعيل وتعطيل)، الفواتير، الديون (تسوية)، الشكاوى، المندوبين وأداؤهم، التقارير (تصدير Excel)، الإعدادات العامة.
- لوحة Super Admin: Audit Log، الجلسات (إنهاء)، العمولة (سجل + تسجيل دفعات)، **إدارة المستخدمين والأدوار** (ترقية أي حساب لمندوب/إداري بدون الحاجة لـ SQL Editor)، **إدارة السياسات** (إضافة نسخ الشروط والأحكام/الخصوصية من الواجهة مباشرة).
- رسائل واتساب الجاهزة (Click-to-Chat) لكل الأحداث المهمة.
- استرجاع كلمة المرور بدون تكلفة.
- رفع الصور عبر Cloudinary بتوقيع آمن.
- بنية Push Notifications (VAPID + Service Worker + جدول الاشتراكات) + Edge Function جاهزة للربط.

## 6. نظام التصميم (Design System) — جديد

المشروع الآن مبني على نظام Design Tokens حقيقي بدل ألوان متفرقة:

- **الألوان/الخطوط/الزوايا/الظلال/الحركة** كلها CSS Variables في `app/globals.css` (قسم `:root` للـLight و`[data-theme='dark']` للـDark) — تغيير الهوية بالكامل يتم من مكان واحد.
- **الخطوط:** Almarai (عربي ناعم مستدير) + Inter (أرقام/لاتيني)، مربوطين بـ`--font-arabic`/`--font-latin`.
- **زر تبديل الثيم:** موجود في كل الـNavigation الثلاثة (`components/theme/ThemeToggle.tsx`)، بدون Flash عند التحميل بفضل `ThemeScript.tsx`.
- **الشعار:** `components/Wordmark.tsx` — 4 نسخ (افتراضي/غامق/فاتح/Compact).
- **الأيقونات:** `components/Icon.tsx` — نظام مخصص بالكامل (~28 أيقونة)، بدون أي مكتبة خارجية.
- **الرسومات التوضيحية:** `components/illustrations/` — أربع رسومات (لا طلبات، نجاح، لا نتائج، صيانة)، تُستخدم عبر `components/EmptyState.tsx`.
- **مكوّنات الحالة:** `components/Badge.tsx` (حالات الطلب/الدين/الشكوى)، `components/OrderTimeline.tsx` (تتبع بصري للطلب بدل نص جامد)، `components/Skeleton.tsx` (تحميل).
- **الأزرار/الحقول/الكروت:** كلاسات عامة في `globals.css` (`.btn-primary`, `.btn-secondary`, `.btn-ghost`, `.btn-danger`, `.card`, `.input`, `.alert-*`, `.badge-*`) داخل `@layer components` — أي صفحة تستخدمها تتحدّث تلقائيًا مع أي تعديل مستقبلي في الهوية.

### تم تطبيق الهوية الكاملة (أيقونات + Badges + Empty States) على:
تسجيل الدخول/الحساب، الرئيسية، التصنيفات/المنتجات، الطلبات (قائمة + تفاصيل مع Timeline)، السلة، الملف الشخصي (عميل/مندوب)، المديونية، الشكاوى، لوحة الإدارة بالكامل (Dashboard، الطلبات، الفواتير، الديون، الشكاوى، المنتجات، التصنيفات، المندوبين، التقارير، الإعدادات)، ولوحة Super Admin بالكامل (المستخدمين، السياسات، العمولة، Audit Log، الجلسات)، ولوحة المندوب (Dashboard + تفاصيل الطلب).

### باقي بنفس الأسلوب (تحديث تجميلي بسيط جدًا، الأساس جاهز 100%):
تفاصيل صغيرة داخل بعض النماذج (ProductForm/CategoryForm) ومكوّنات الأزرار الصغيرة (SettleDebtButton، RevokeSessionButton...) لسه بتستخدم نص عادي بدل أيقونة، لكنها **شغّالة وتظهر بالهوية الجديدة بالكامل** (الألوان/الخطوط/الزوايا) لأنها تعتمد على نفس الـTokens والـClasses العامة.

### قيود معروفة في هذه المرحلة (Design v1):
- الأيقونات والرسومات التوضيحية مبنية يدويًا كـSVG بسيطة تخدم الاتجاه المطلوب (Soft Rounded + Geometric)، وليست تصميم استوديو احترافي — قابلة للاستبدال بسهولة بملفات SVG من مصمم لاحقًا بنفس الأسماء في `components/Icon.tsx`.
- الـNavigation الإداري حاليًا Top Bar منظم بمجموعات (وليس Sidebar ثابت جانبي) لتفادي إعادة هيكلة كل صفحات لوحة التحكم؛ يمكن تطويره لاحقًا لـSidebar حقيقي كخطوة منفصلة.
- أيقونات PWA (`icon-192.png`, `icon-512.png`) لسه مطلوب تصميمها فعليًا كملفات صور.

## 6.1 تحديث الهوية اللونية (أسود محايد + Neon)

بناءً على طلب تعديل، تم استبدال الألوان الأساسية:

- **الوضع الفاتح:** خلفية بيضاء حقيقية (`#FFFFFF`) بدل الأبيض الدافئ القديم. الأزرار الأساسية وحدود الكروت والنصوص القوية بقت بلون أسود محايد (`--color-ink: #131315`) بدل التركواز — مش أسود "كحلي"، لون محايد تمامًا.
- **الوضع الداكن:** خلفية سوداء كلاسيكية مريحة للعين (`#141416`) بدل الأسود المائل للتركواز القديم. الأزرار الأساسية بقت بيضاء (Ink معكوس) على الخلفية السوداء.
- **الـAccent (تركواز):** باقي كما هو لكن بدور أضيق ومركّز أكتر — يُستخدم للروابط، الحالة النشطة في القوائم، وأهم حاجة: **توهج Neon** (`--color-accent-neon`) على العناصر التفاعلية المهمة (الزر الأساسي عند الـHover، الكرت القابل للنقر، الخطوة الحالية في متابعة الطلب، الرابط النشط في القوائم، حلقة التركيز عند الكتابة في أي حقل).
- كل التغيير ده تم من مكان واحد فقط (`app/globals.css`) بحكم نظام الـTokens — مفيش أي صفحة اتعدّلت يدويًا عشان تاخد الألوان الجديدة.

## 6.2 تعديلات هيكلية جديدة

- **صورة وترتيب كل تصنيف:** من `/admin/categories` دلوقتي تقدر: تضيف/تغيّر صورة أي تصنيف موجود بالفعل (مش بس وقت الإنشاء)، وتحرّكه لأعلى/لأسفل في الترتيب (بيغيّر `sort_order` في القاعدة مباشرة، وده اللي بيتحكم في ترتيب ظهور التصنيفات للعميل).
- **"منتجات ناس كتير طلبتها" في الصفحة الرئيسية:** قسم جديد تحت التصنيفات في `/home`، بيعرض المنتجات الأكثر طلبًا عبر كل العملاء (بيانات مجمّعة، مفيهاش أي خصوصية) مع زر إضافة سريع للسلة — عشان العميل يفتكر حاجة كان ناوي يطلبها. مبني على دالة SQL جديدة `get_popular_products` (ملف `0023`).

## 6.3 البوت المساعد — مؤجّل لمرحلة منفصلة

تم الاتفاق على تأجيل بناء البوت المساعد (بحث عن طلب، متابعة الطلب، وخوارزميات مخصصة بدل الاعتماد الكامل على نموذج ذكاء اصطناعي جاهز) لمرحلة لاحقة منفصلة، بعد استقرار باقي التعديلات.

## 6.4 تعديلات UX/تصميم إضافية (V2)

- **تصفّح عام بدون تسجيل دخول إجباري:** كان فيه Bug فعلي بيوجّه أي زائر مباشرة لصفحة تسجيل الدخول حتى لو بس عايز يتصفّح. دلوقتي `/home`، `/categories`، `/products`، `/cart` كلها متاحة بدون حساب. تسجيل الدخول بيتطلب فقط عند خطوة "تأكيد الطلب" (`/checkout`) أو أي صفحة شخصية (طلباتي، حسابي، الديون).
- **العودة لنفس الخطوة بعد تسجيل الدخول:** لو زائر وصل لصفحة محمية وهو مش مسجّل، بيتوجّه لصفحة الدخول ثم يرجع تلقائيًا لنفس المكان اللي كان فيه بعد الدخول أو التسجيل (`returnTo`)، والسلة بتفضل محفوظة لأنها بتتخزن في الذاكرة أثناء التنقل العادي داخل الموقع.
- **تأكيد كلمة المرور عند التسجيل:** حقل "تأكيد كلمة المرور" بقى إلزامي، مع رسالة واضحة وودودة لو مش متطابقين.
- **إظهار/إخفاء كلمة المرور:** مكوّن `PasswordInput` موحّد بأيقونة عين مخصّصة (من نفس نظام الأيقونات)، مطبّق في تسجيل الدخول، إنشاء الحساب (الحقلين)، واسترجاع كلمة المرور (الحقلين).
- **تقليل هيمنة اللون التركواز:** كان فيه إفراط في استخدام خلفيات تركواز صريحة لكل أيقونة تقريبًا (عناوين الصفحات، بطاقات المنتجات، التصنيفات). `IconBadge` بقى افتراضيًا محايد (رمادي فاتح/غامق حسب الثيم) بدل التركواز، والتركواز بقى محجوز فقط للحالات المهمة فعلاً (رابط، حالة نشطة، أو تمييز مقصود واحد في الصفحة).
- **تقليل توهج Neon الزائد:** كان فيه توهج قوي حوالين كل زرار وكارت وحقل عند التركيز. بقى محدود جدًا وهادئ (حدود/ظل بسيط بدل التوهج المضاعف).

## 6.5 المرحلة الأولى من الميزات الجديدة (اللون + المندوب + الدفع الأونلاين)

- **اللون المميّز:** الهوية اتحوّلت من التركواز للكهرماني/الذهبي الدافئ (`--color-accent`)، مع تمييز واضح عن لون التحذير (Warning) اللي بقى برتقالي محروق بدل ما يتشابه مع الذهبي الجديد. التغيير ده اتعمل من مكان واحد بس (`app/globals.css`) وبيغطي كل المشروع تلقائيًا.

- **رفض المندوب للطلب بسبب (بدل التوجيه اليدوي):** التعيين لسه تلقائي بالكامل زي ما هو (`fn_pick_agent`/`assign_next_agent`) — احنا اللي بنحدد الخوارزمية، مش المندوب بيختار. لكن دلوقتي المندوب يقدر يرفض الطلب **حتى أثناء مرحلة الشراء** (مش بس التوصيل) بسبب إلزامي عبر دالة جديدة `decline_shopping_assignment`، والطلب يتحول تلقائيًا لمندوب تاني بنفس الخوارزمية. الزرار موجود في شاشة الشراء بتاعت المندوب.
  > ملحوظة: فكرة "تقديم مندوبين جدد" (نموذج تقديم وظيفة) اتأجلت بناءً على طلبك.

- **نظام الدفع الأونلاين (تحقق يدوي، مش بوابة دفع حقيقية):**
  - من `/admin/settings` تقدر تدخل بيانات المحفظة الإلكترونية وInstaPay (الرقم/الاسم).
  - عند اختيار العميل "محفظة" أو "InstaPay" في الدفع، بتظهر له البيانات دي جاهزة للنسخ، مع تنبيه واضح إن المبلغ المُحوَّل تقريبي وإن السعر النهائي هيتحدد بعد ما المندوب يشتري وتُعتمد الفاتورة.
  - العميل بيرفع صورة التحويل + اسمه ورقمه، وده بيتحفظ مع الطلب في نفس لحظة الإرسال (Transaction واحدة عبر `create_order` المُحدَّثة).
  - الإدارة (Business/Super Admin) بتشوف صورة الإثبات في صفحة تفاصيل الطلب وتقدر "تأكيد الاستلام" أو "رفض" عبر `review_payment_proof`.
  - العميل بيشوف حالة التحويل (بانتظار المراجعة/تم التأكيد/مرفوض) في صفحة طلبه.

## 6.6 المرحلة الثانية (الفوتر + البانر + الإرشادات + المديونية)

- **الفوتر:** ظاهر أسفل الصفحة الرئيسية — روابط الشروط والأحكام/الخصوصية (`/legal/terms`, `/legal/privacy` — صفحتان عامتان بتقرأان من جدول `policies` مباشرة)، روابط تشغيلية سريعة، ومنطقة الخدمة.
- **بانر الصفحة الرئيسية:** من `/admin/settings` تقدر ترفع صورة بانر تظهر أعلى الصفحة الرئيسية فوق الـHero. لو مفيش بانر مرفوع، الـHero التوضيحي بيظهر عادي.
- **شريط الإعلانات:** تفعيل/تعطيل + نص حر من `/admin/settings`، بيظهر تلقائيًا أسفل شريط تنقل العميل في كل صفحاته (مش بس الرئيسية) لو مفعّل.
- **الإرشادات المنبثقة (Onboarding):** نافذة بـ3 خطوات بسيطة تظهر تلقائيًا أول ما العميل يفتح الصفحة الرئيسية (مرة واحدة فقط، محفوظة في `localStorage`)، بزرار "تخطي" كامل أو "التالي" خطوة بخطوة.
- **المديونية بقت جوه الحساب:** اتشالت من شريط التنقل الرئيسي (كانت تبويب مستقل)، وبقت ملخّص صغير هادئ داخل صفحة "حسابي" (رقم بس، من غير تنبيه أو لون تحذيري لو مفيش دين) بيودّي لصفحة `/debts` التفصيلية لو حبّ العميل يشوف أكتر.

## 6.7 المرحلة الثالثة (الخصومات + العروض + Push فعليًا + شكل التصنيفات)

- **خصومات التوصيل:** من `/admin/discounts` — خصم عام (كل العملاء) أو لعميل واحد محدد، نسبة % أو قيمة ثابتة، بيتطبّق تلقائيًا على رسوم التوصيل عند إنشاء أي طلب جديد. الرسوم الأصلية بتتحفظ في `delivery_fee_original` عشان التاريخ المالي يفضل دقيق.
- **العروض المشروطة:** من `/admin/promotions` — النوع المبني حاليًا "لو العميل طلب X مرات خلال Y ساعة" (قابل للتوسع لاحقًا بأنواع شروط تانية بدون تعديل الجدول، بحكم تصميم `condition_type`/`condition_config` كـ jsonb). المكافأة بتتطبّق على **رسوم التوصيل فقط** (مش قيمة المنتجات — قرار مقصود موضّح في الكود لأن المنتجات بتُشترى فعليًا بفلوس حقيقية). العرض ممكن يكون عام أو لعملاء محددين، ومحفوظ ليه سجل استفادة (`promotion_redemptions`) يمنع تكرار الاستفادة في نفس النافذة الزمنية.
- **إظهار العروض للعميل بشكل ملفت:** مكوّن `PerksAlert` بيظهر في الرئيسية والدفع — لو عنده خصم فعّال بيوريهولك، ولو قريب من عرض مشروط بيقوله "باقيلك كام طلب".
- **أكثر العملاء طلبًا:** جدول جديد في `/admin/reports` (أفضل 10) + تصدير Excel كامل، عبر دالة `get_top_customers`.
- **إشعارات Push فعليًا:** بقت متربطة بأهم الأحداث (طلب جديد ← تنبيه فوري لكل الإداريين، قبول/رفض الطلب، الفاتورة جاهزة، في الطريق، تم التسليم، الإلغاء، مديونية جديدة) — كل حدث بيسجّل في `notification_log` بـ`channel='push'` تلقائيًا. **يبقى مطلوب منك خطوة واحدة بس:** ربط الـWebhook من لوحة Supabase زي الموضّح في القسم 7 تحت، وإلا الإشعارات هتتسجّل بس مش هتوصل فعليًا للموبايل.
- **شكل التصنيفات:** بقت بأحجام متنوعة (Bento-style) بدل شبكة موحّدة، والتصنيف اللي ليه صورة بيظهرها كخلفية كاملة للكارت مع تدرّج واسمه فوقها، بدل أيقونة صغيرة جنب الاسم.

## 7. المتبقي / يحتاج إكمالًا قبل الإطلاق الفعلي ⚠️

- **ربط Edge Function الخاصة بالـ Push فعليًا**: أنشئ Database Webhook من لوحة Supabase (Database → Webhooks) على جدول `notification_log`، الحدث `INSERT`، الشرط `channel = 'push'`، ووجّهه لدالة `send-push`، **وأضف للـ Webhook الـ Header `x-webhook-secret` بنفس قيمة السر `SEND_PUSH_WEBHOOK_SECRET`** (خطوات تعيين السر في قسم الأمان 9.2). الدالة بترفض أي طلب من غير السر ده.
- **اختبارات E2E للواجهة** — لم تُبنَ بعد. اختبارات الوحدة للمنطق الأمني موجودة في `tests/` (شغّلها بـ `npm test`).
- **أيقونات PWA** (`/public/icon-192.png`, `/public/icon-512.png`) غير موجودة فعليًا — أضف تصميم الشعار عند توفره (جزء من مرحلة الثيم القادمة).
- ✅ ~~إنشاء أول Super Admin يدويًا~~ — أصبح ممكنًا الآن ترقية أي حساب من `/super/users` بعد إنشاء أول Super Admin واحد فقط يدويًا (خطوة لمرة واحدة لا يمكن تفاديها لأسباب أمنية).
- ✅ ~~الشروط والأحكام~~ — أصبحت تُضاف من `/super/policies` مباشرة بدل SQL Editor.

## 9. الأمان

### 9.1 ما يفعله ملف `0046_security_hardening.sql`
- سحب صلاحية تنفيذ كل دوال قاعدة البيانات من الجمهور (`public`/`anon`/`authenticated`) ثم منح صريح لكل دالة للأدوار المسموحة فقط. الدوال الداخلية (`fn_transition_order`, `fn_queue_push`, `fn_log_audit`, `fn_create_cancellation_debt`, `assign_next_agent`, `fn_pick_agent`) لا يستدعيها أي دور من الواجهة.
- **أي دالة جديدة تُضاف لاحقًا لازم تاخد `grant execute` صريح**، وإلا الواجهة مش هتقدر تستدعيها (ده مقصود).
- إغلاق الكتابة المباشرة على `orders` و`order_items` و`audit_log` و`password_reset_tokens` — كل الكتابة عبر دوال RPC.
- منع تعديل `role` و`status` و`phone` في `users` مباشرة من المستخدم نفسه، ومنع تعديل عداد الطلبات النشطة للمندوب.
- استرجاع كلمة المرور: عميل ← أي إداري، مندوب/Business Admin ← Super Admin فقط، Super Admin ← غير متاح من هذا المسار. الرمز يُلغى بعد الاستخدام وتُنهى كل جلسات المستخدم.
- حد أقصى للطلبات النشطة لكل عميل (الافتراضي 5). لتغييره: `insert into public.platform_settings (key, value) values ('max_active_orders_per_customer', '8'::jsonb) on conflict (key) do update set value = excluded.value;`
- الجلسات في `/super/sessions` صارت حقيقية: الإنهاء بيحذف الجلسة من Supabase Auth، وحظر المستخدم بينهي كل جلساته.

### 9.2 خطوات يدوية مطلوبة بعد النشر
1. **سر الـ Webhook:** اعمل سر عشوائي طويل ثم:
   ```
   supabase secrets set SEND_PUSH_WEBHOOK_SECRET=<السر>
   supabase functions deploy send-push
   ```
   وأضف نفس القيمة كـ Header باسم `x-webhook-secret` في إعداد الـ Database Webhook.
2. **Supabase → Authentication:** اضبط الحد الأدنى لطول كلمة المرور على 8 أو أكثر، وراجع حدود المحاولات (Rate Limits)، وقلّل مدة صلاحية الـ JWT (مثلاً 900–3600 ثانية) لأن إنهاء الجلسة بيقطع التجديد وليس التوكن الحالي.
3. **Cloudinary:** حدّد الحد الأقصى لحجم الصور من إعدادات الحساب أو الـ Upload Preset — الحد ده مش ممكن يتفرض من الكود.
4. بعد أي نشر، افتح الموقع وراجع الكونسول للتأكد إن سياسة الـ CSP (في `next.config.js`) مش بتمنع أي مورد جديد أضفته.
