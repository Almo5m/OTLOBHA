# المنيب جو — almoneib-go (الإصدار 2: طلب بدون حسابات)

خدمة توصيل محلية (المنيب — مصر). Next.js 15 (App Router) + Supabase (Postgres/Auth/RLS) + Cloudinary + Vercel.

> **التغيير الجذري في الإصدار 2:** مفيش حسابات عملاء. العميل بيكتب طلبه واسمه ورقمه وعنوانه (واللوكيشن اختياري) ويبعت. الطلب بيوصل لكل الإداريين، وأول واحد يستلمه يكمله. بعد التسليم بتتولّد فاتورة صورة تتبعت للعميل على واتساب وتتخزّن للإدارة.
> النسخة القديمة (بالحسابات والديون والخصومات) محفوظة في `supabase/_old/` و`docs/_old/` للرجوع فقط.

---

## 1. رحلة الطلب

**العميل:** يدخل الموقع ← يكتب أصنافه (نص حر، أو من الكتالوج لو مفعّل) ← الاسم + الرقم + العنوان (+ لوكيشن + ملاحظات) ← إرسال. بيتحوّل لصفحة متابعة برابط خاص `/order/<token>` (الرابط هو الطريقة الوحيدة للرجوع للطلب، وبيتحفظ كمان في «طلباتي» على نفس الجهاز).

**الإدارة (مندوب / أدمن / سوبر أدمن — نفس الخطوات للجميع):**

| # | الخطوة | الحالة |
|---|--------|--------|
| 1 | الطلب بيظهر عند الكل لحظيًا. أول واحد يضغط **استلام الطلب** ياخده (قفل في الداتابيز، والباقي يشوفه اختفى) | `new_order` ← `shopping` |
| 2 | يبعت **رسالة المتابعة** للعميل (واتساب، رابط المتابعة جاهز) — إجباري قبل تسجيل الأسعار | `shopping` |
| 3 | يسجّل السعر الفعلي لكل صنف (متوفر / مش متوفر) ثم **في الطريق للعميل** | `shopping` ← `on_the_way` |
| 4 | **تم تسليم الطلب** ← الفاتورة بتتولّد أوتوماتيك وبتتبعت للعميل | `on_the_way` ← `delivered` |

- لو اتاخد بالغلط: **رجّع الطلب للكل** (بيمسح الأسعار ويرجع لـ `new_order`).
- الأدمن/السوبر أدمن يقدروا **يلغوا** الطلب بسبب. العميل يقدر يلغي من صفحة المتابعة **قبل** ما حد يستلمه فقط.
- مفيش تأكيد استلام فلوس ولا اعتماد فاتورة ولا مراجعة/قبول منفصل — اتشالوا.

## 2. الفاتورة

- بتتولّد كصورة (Canvas في متصفح الإداري — عشان العربي يطلع سليم على iOS وأندرويد) وبتترفع على **Cloudinary**، ورابطها بيتخزّن في `invoices.image_url`.
- **إرسال:** الزرار بيفتح قائمة مشاركة الموبايل بالصورة (الإداري يختار شات العميل) — لازم يتجرب على جهاز حقيقي. زرار تاني يفتح شات العميل مباشرة برابط الفاتورة. مفيش WhatsApp API مدفوع؛ الإرسال يدوي بضغطة.
- **الأرشيف:** `/admin/invoices` — بحث برقم العميل أو اسمه أو رقم الفاتورة، وإعادة إرسال أي فاتورة قديمة.
- الاسم وجملة آخر الفاتورة من `/admin/settings`، وقالب رسالة الفاتورة من جدول `whatsapp_templates` (`invoice_sent`).

## 3. الحماية من الطلبات الوهمية

بدل الحسابات: حد للطلبات الجارية (افتراضي 3) وحد يومي (افتراضي 10) لكل **رقم موبايل** و**معرّف جهاز** (`localStorage`)، وعلى **IP** بحد أوسع 5 أضعاف. بيتطبّق جوه `create_guest_order` في الداتابيز نفسها (مش في الواجهة) وبيتعدّل من `/admin/settings`. معرّف الجهاز ممكن يتمسح، فالحد الأساسي فعليًا على الرقم.

## 4. الإعداد الأولي

### أ) Supabase (مشروع جديد فاضي)
1. أنشئ مشروعًا جديدًا على [supabase.com](https://supabase.com).
2. من **SQL Editor** شغّل بالترتيب: `supabase/schema.sql` ثم `supabase/seed.sql`.
3. **Authentication → Sign In / Providers → Email:** فعّل Email/Password، و**عطّل "Allow new users to sign up"** (الحسابات بتتعمل من لوحة السوبر أدمن بس).
4. من **Settings → API** انسخ `Project URL` و`anon key` و`service_role key`.

### ب) Cloudinary
حساب مجاني، وانسخ Cloud Name وAPI Key وAPI Secret. (بيستخدم لصور الكتالوج وصور الفواتير وصور التحويل.)

### ج) متغيرات البيئة
انسخ `.env.example` إلى `.env.local` واملأه. لتوليد مفاتيح VAPID: `npx web-push generate-vapid-keys`.

### د) أول سوبر أدمن (مرة واحدة)
مفيش صفحة تسجيل، فأول حساب بيتعمل يدويًا:
1. **Authentication → Users → Add user:** البريد `01xxxxxxxxx@otlobha.local` (رقمك مكان الأصفار) + كلمة مرور، وفعّل Auto Confirm.
2. من **SQL Editor**:
   ```sql
   insert into public.users (id, phone, full_name, role)
   select id, '01xxxxxxxxx', 'اسمك', 'super_admin'
   from auth.users where email = '01xxxxxxxxx@otlobha.local';
   ```
3. ادخل من `/login` بالرقم وكلمة المرور. بعدها كل الحسابات التانية من `/super/users` (اسم + رقم + دور + كلمة مرور مؤقتة).

### هـ) التشغيل
```bash
npm install
npm run dev      # http://localhost:3000
npm test         # اختبارات المنطق
```
النشر: `vercel` + نفس متغيرات البيئة. اضبط `NEXT_PUBLIC_SITE_URL` على الدومين الفعلي (بيدخل في روابط المتابعة والمشاركة).

### و) إشعارات Push للإداريين
`notification_log` بيتسجّل فيه إشعار لكل إداري نشط عند: طلب جديد، رجوع طلب للكل، إلغاء العميل، شكوى جديدة. عشان توصل فعليًا:
1. `supabase secrets set SEND_PUSH_WEBHOOK_SECRET=<سر عشوائي طويل>` ثم `supabase functions deploy send-push`.
2. **Database → Webhooks:** جدول `notification_log`، الحدث `INSERT`، الشرط `channel = 'push'`، الدالة `send-push`، وHeader باسم `x-webhook-secret` بنفس السر.

## 7. قرارات تصميم مهمة

- **لا يوجد Phone OTP:** الإداريين بيدخلوا برقم الموبايل + كلمة مرور (بريد داخلي وهمي `رقم@otlobha.local`). الرقم الحقيقي في `public.users.phone`.
- **الكتابة على `orders` والفواتير كلها عبر دوال RPC** (`create_guest_order`, `claim_order`, `release_order`, `start_delivery`, `mark_delivered`...). مفيش UPDATE مباشر من الواجهة، والزائر مبيقدرش يقرا أي طلب غير بالرابط الخاص (`get_order_by_token`).
- **رابط المتابعة** = رمز عشوائي من 64 حرف (244 bit) — مستحيل يتخمّن، لكن أي حد معاه الرابط يشوف الطلب، فمتشاركوش علنًا.
- **أي دالة جديدة** لازم تاخد `grant execute` صريح في آخر `schema.sql`.
- **الكتالوج:** السوبر أدمن يتحكم فيه من `/admin/products` و`/admin/categories`، ويقدر يخفي التصنيفات من الإعدادات (`categories_visible`) لحد ما يتجمّع كتالوج كبير.
- كل عملية حساسة بتتسجّل في `audit_log` داخل نفس الـ Transaction.
