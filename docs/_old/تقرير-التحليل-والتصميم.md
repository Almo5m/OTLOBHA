# تقرير التحليل والتصميم المعماري — مشروع «المنيب جو»
### الإصدار 1.0 — مرحلة ما قبل التنفيذ

هذا التقرير يغطي البنود المطلوبة في القسم 61 و64 من وثيقة المتطلبات. تم تحليل الوثيقة كاملة، ولا يتضمن هذا المستند أي كود، بل قرارات تصميم يجب اعتمادها قبل البدء بالتنفيذ.

---

## A. تحليل المتطلبات والتعارضات المكتشفة

بعد قراءة الوثيقة كاملة، لم أجد تعارضات جوهرية تكسر منطق العمل، لكن وجدت عدة نقاط تحتاج توضيحًا أو تحتوي على غموض بسيط تم حله بافتراضات منطقية (موضحة أدناه)، بالإضافة إلى نقطتين أعتبرهما "مشاكل" حقيقية يجب معالجتها بشكل مختلف عمّا هو مذكور حرفيًا:

### A.1 — مشكلة أمنية: استرجاع كلمة المرور عبر الإدارة (القسم 10)
الوثيقة تنص على أن الإدارة "تتحقق من بيانات العميل" ثم "تعيد تعيين كلمة المرور". هذه العملية إذا نُفذت عبر واجهة تسمح للإدارة برؤية كلمة المرور الجديدة أو اختيارها يدويًا، تفتح ثغرة: أي موظف يمكنه انتحال شخصية أي عميل بعد إعادة التعيين مباشرة دون علم العميل.

**الحل المعتمد (مؤكَّد، صفر تكلفة):** لا تقوم الإدارة بـ"تعيين" كلمة مرور، بل النظام يُصدر **رابط إعادة تعيين ذو صلاحية محدودة (زمنيًا واستخدامًا لمرة واحدة)** بعد أن يتحقق الموظف من هوية العميل هاتفيًا. الرابط يُرسل **بنفس آلية القسم F أعلاه** (رسالة جاهزة + Click-to-Chat يدوي عبر واتساب المندوب/الإداري) — لا حاجة لأي API أو SMS مدفوع. العميل نفسه من يضع كلمة المرور الجديدة عند فتح الرابط. هذا يحافظ على مبدأ "لا أحد يعرف كلمة مرور العميل" حتى الإدارة، ويُسجَّل في Audit Log فقط "تم إصدار وإرسال رابط إعادة تعيين" وليس كلمة المرور. يتطلب فقط جدول tokens قصير الأجل (nullable/expiring)، بدون أي تكلفة إضافية.

### A.2 — تعارض ضمني: "الطلب اليدوي" و"إجمالي الطلب المعروض قبل التأكيد"
القسم 15/16/17 يقول إن السعر الظاهر للمنتجات من الكتالوج "ليس نهائيًا"، لكن المنتج اليدوي **لا يوجد له سعر ظاهر على الإطلاق** (العميل لا يعرف السعر إطلاقًا وقت الطلب). هذا ليس خطأً، لكنه يعني أن "الإجمالي المتوقع" الذي يراه العميل عند المراجعة (القسم 20/21) سيكون **تقديريًا فقط** لأنه لا يشمل قيمة الأصناف اليدوية. يجب توضيح هذا للعميل بشكل صريح في شاشة المراجعة (وليس فقط رسالة عامة عن تغيّر الأسعار)، حتى لا يتفاجأ برقم فاتورة نهائي مختلف جدًا عن توقعه. هذا قرار تصميم UX وليس تعارضًا يحتاج حلًا هندسيًا، لكن وجب ذكره لأنه يمس الثقة مع العميل.

### A.3 — غموض تم حله بافتراض منطقي: من يعتمد الفاتورة؟
القسم 28 يقول "يتم عرض الفاتورة للإدارة/المستخدم المسؤول" دون تحديد من بالضبط بين (المندوب نفسه، Business Admin). بما أن قاعدة "لا دفع مقدم" و"لا تعديل بعد الاعتماد" تحتاج رقابة، **الافتراض المعتمد:** تسجيل السعر الفعلي متاح لكل من المندوب وBusiness Admin وSuper Admin (**حسب التحديث المتفق عليه** — مفيد في حال قام أحد الإداريين بتصحيح سعر أو بالشراء بنفسه)، لكن **اعتماد الفاتورة يبقى صلاحية Business Admin/Super Admin فقط** (وليس المندوب) لضمان فصل الأدوار (Separation of Duties) بين من يُنفق ومن يُعتمد — وهذا مبدأ أساسي في أي نظام مالي، ويمنع تضارب المصالح حتى لو كان نفس الشخص يشتري ويُدخل الأسعار.

### A.4 — غموض محلول: هل "التعيين الذكي" يعمل تلقائيًا فورًا أم يحتاج تدخل؟
بما أن حاليًا "صاحب النشاط نفسه هو المندوب الوحيد فعليًا"، فإن التعيين التلقائي في المرحلة الحالية سيكون بسيطًا (مندوب واحد متاح دائمًا تقريبًا)، لكن النظام يجب أن يُبنى بمنطق التعيين الكامل من اليوم الأول (وليس Hardcoded لمندوب واحد) حتى لا نحتاج إعادة هندسة عند إضافة مندوبين جدد. **هذا قرار معماري مهم:** سيتم تنفيذه كخدمة تعيين مستقلة (Assignment Service) قابلة للاستبدال أو التطوير لاحقًا دون المساس بجدول الطلبات.

### A.5 — نقطة تحتاج تأكيدًا: خصوصية "نقل الطلب" أمام العميل
القسم 31 ينص على إخفاء تفاصيل النقل عن **المندوب الجديد**، لكن لم يُذكر هل يُخفى ذلك عن **العميل** أيضًا. الافتراض المعتمد: يُخفى عن الطرفين (المندوب والعميل) للحفاظ على تجربة سلسة، ويبقى ظاهرًا فقط لـ Super Admin عبر Audit Log — هذا هو الأكثر اتساقًا مع روح القسم 31.

## B. القرارات التي تحتاج قرارًا بشريًا فعليًا (Missing Decisions)

هذه فقط القرارات التي لا يمكن استنتاجها منطقيًا وتحتاج موافقتكم الصريحة قبل التنفيذ:

1. **قناة إرسال WhatsApp Automation:** هل نبدأ بحل غير رسمي منخفض التكلفة (مثل ربط عبر مكتبات WhatsApp Web غير الرسمية) رغم مخاطر الحظر، أم نبدأ مباشرة بمزود رسمي (WhatsApp Cloud API من Meta وهو **مجاني ضمن حصة شهرية** للرسائل المُبادَر بها من العميل، ومنخفض التكلفة لما بعد ذلك)؟ — **يوجد تفصيل كامل في القسم F أدناه.**
2. **Hosting/الاستضافة والميزانية الشهرية المتاحة** — يحدد اختيار Supabase Plan (Free/Pro) وطريقة استضافة الواجهة الأمامية.
3. **نطاق الدومين (Domain)** المطلوب للمنصة (يؤثر على PWA/SEO/WhatsApp Business verification لاحقًا).
4. **رقم WhatsApp Business** الذي سيُستخدم فعليًا كمرسِل — يجب أن يكون مرتبطًا برقم هاتف حقيقي مخصص لا يُستخدم على واتساب شخصي عادي بالتوازي.
5. **آلية تسوية العمولة الفعلية بين Super Admin وBusiness Admin:** هل التسوية نقدية يدوية تُسجَّل فقط، أم أن هناك تحويلًا بنكيًا/محفظة يجب ربطها لاحقًا؟ (يؤثر فقط على حقل "ملاحظات" في سجل الدفع، ليس على البنية).
6. **نسبة/قيمة مديونية الإلغاء الابتدائية** الافتراضية عند الإطلاق (رقم فعلي تضعه الإدارة، وليس قرارًا تقنيًا).

كل ما عدا ذلك من تفاصيل تم حسمه بافتراضات موثقة في هذا التقرير.

## C. Architecture Proposal

### المبدأ العام
نظام Sequential Workflow قائم على الأحداث، حيث كل انتقال حالة هو نتيجة فعل حقيقي (Trigger)، منفّذ عبر **Database Functions/Triggers + Edge Functions** وليس منطقًا مبعثرًا في الواجهة الأمامية. هذا يضمن أن حالة الطلب لا يمكن كسرها حتى لو تم استدعاء الـ API مباشرة.

| الطبقة | الاختيار | السبب |
|---|---|---|
| **Frontend** | Next.js (React) + PWA (installable, offline shell, push) | يخدم Customer وBusiness Admin وDelivery Agent بواجهة واحدة متجاوبة، مع دعم PWA الأصلي (manifest + service worker) لتثبيت التطبيق على موبايل المندوب دون متجر تطبيقات |
| **Backend/API** | Supabase (Postgres + Auto REST/RPC + Edge Functions بـ Deno/TypeScript) | يقلل زمن التطوير، ويوفر RLS أصيلاً على مستوى قاعدة البيانات (أهم نقطة أمان في هذا المشروع بالذات لأنه يحتوي بيانات مالية) |
| **Database** | Postgres (عبر Supabase) | دعم كامل لـ Row Level Security، Triggers، Views، JSONB للـ Snapshots |
| **Authentication** | Supabase Auth (Phone/Password، بدون OTP حاليًا كما هو مطلوب) + Custom Claims للأدوار | يدعم لاحقًا تفعيل OTP دون تغيير هيكلي |
| **Storage** | Cloudinary (صور المنتجات/التصنيفات وأي صور مستقبلية) | **قرار مُحدَّث حسب الاتفاق.** حساب Cloudinary Free tier يكفي لهذه المرحلة (تحويل/ضغط تلقائي للصور مفيد جدًا لسرعة تحميل الكتالوج على الموبايل). قاعدة البيانات تخزّن فقط الـ `secure_url` وليس الملفات نفسها |
| **Notifications (Push)** | Web Push API (VAPID) عبر Service Worker — مدمج ضمن PWA بدون تكلفة خارجية | مجاني بالكامل، ويعمل على Android مباشرة؛ iOS يدعمه أيضًا (Safari 16.4+) عند تثبيت الـ PWA |
| **WhatsApp** | **رسائل معدّة مسبقًا (Prepared Messages) يرسلها المندوب/الإداري يدويًا عبر رابط Click-to-Chat** — بدون API مدفوع | قرار مُحدَّث بسبب غياب الميزانية. تفصيل كامل في القسم F (تم تحديثه) |
| **Hosting** | Frontend على Vercel + Backend/DB على Supabase Cloud | فصل concerns، Scaling تلقائي، تكلفة تبدأ من Free tier — **مؤكَّد** |
| **Security Layer** | RLS كخط دفاع أول + Edge Functions كخط دفاع ثانٍ للعمليات المالية الحساسة (اعتماد فاتورة، تسوية عمولة) | لا تُنفَّذ أي عملية مالية حساسة عبر REST مباشر من الواجهة، بل عبر RPC محكوم بمنطق سيرفر |

### لماذا Supabase وليس بناء Backend مخصص؟
المشروع يحتاج RLS دقيق جدًا (4 أدوار، كل دور يرى جزءًا مختلفًا من نفس الجدول)، وAudit Log صارم، وSnapshots تاريخية. Supabase يعطي هذا "جاهزًا" على مستوى قاعدة البيانات نفسها بدل إعادة بناء طبقة تفويض في كود التطبيق (وهي مصدر شائع للثغرات). ميزة إضافية: Realtime channels مفيدة لتحديث حالة الطلب لحظيًا عند العميل والمندوب دون Polling.

## D. Database Design Proposal

تصميم مبني بالكامل على المتطلبات (بدون قوالب جاهزة). المفتاح الأساسي لكل الجداول: `uuid`. كل الجداول المالية/التاريخية **immutable بعد نقطة معينة** (Append-only حيثما أمكن).

### D.1 — المستخدمون والأدوار
- **`users`**: id, phone (unique, مطابق لصيغة مصرية), full_name, password_hash, role (`super_admin`|`business_admin`|`delivery_agent`|`customer`), status (`active`|`blocked`|`suspended`), created_at
- **`customer_profiles`**: user_id (FK), default_address_id (FK → addresses), notes
- **`agent_profiles`**: user_id (FK), availability_status (`available`|`busy`|`offline`), current_active_orders_count (denormalized للتعيين السريع)
- **`addresses`**: id, customer_id, label, full_address_text, is_default, created_at, updated_at *(هذا الجدول للعنوان "الحي" القابل للتعديل — لا يُستخدم مباشرة في الطلب، بل يُنسخ)*

### D.2 — الكتالوج
- **`categories`**: id, name, image_url, description, is_active, sort_order, created_at
- **`sale_units`**: id, name (قطعة/كيلو/جرام...), created_at
- **`products`**: id, category_id, name, image_url, description, sale_unit_id, last_known_price (numeric), status (`active`|`inactive`), created_at, updated_at
- **`product_price_history`**: id, product_id, price, source_invoice_item_id (FK), recorded_at *(append-only — كل سعر فعلي مُعتمد يُضاف هنا، و`last_known_price` في products يُحدَّث كـ cache فقط)*

### D.3 — الطلبات (جوهر النظام)
- **`orders`**: id, order_number (تسلسلي قابل للقراءة), customer_id, status (enum — القسم F)، delivery_address_snapshot (JSONB — نسخة كاملة من العنوان وقت الإنشاء)، payment_method (`cash`|`wallet`|`instapay`)، payment_status (`unpaid`|`paid`)، delivery_fee_applied (numeric — قيمة مجمّدة وقت الإنشاء)، previous_debt_applied (numeric)، assigned_agent_id، policy_version_accepted، policy_accepted_at، created_at، accepted_at، delivered_at، canceled_at، cancellation_reason، canceled_by
- **`order_items`**: id, order_id, product_id (nullable — null إذا كان يدويًا), item_type (`catalog`|`manual`), manual_name (nullable), quantity, unit_id, customer_comment, displayed_price_snapshot (نسخة السعر الظاهر وقت الإضافة — لأغراض العرض فقط)، actual_price (nullable حتى الشراء)، is_available (nullable حتى الشراء)، unavailable_reason
- **`order_transfers`**: id, order_id, from_agent_id, to_agent_id, reason, transferred_at *(هذا الجدول مرئي فقط لـ Super Admin عبر Audit Log — لا واجهة مباشرة له)*
- **`order_status_history`**: id, order_id, from_status, to_status, changed_by, reason (nullable), changed_at *(سجل انتقال الحالات — منفصل عن Audit Log العام لسهولة بناء Timeline للطلب)*

### D.4 — الفواتير
- **`invoices`**: id, order_id, invoice_number, status (`draft`|`approved`|`canceled`), items_total, delivery_fee, previous_debt_included, grand_total, payment_method, payment_status, approved_by, approved_at, canceled_reason, superseded_by_invoice_id (للربط بين الفاتورة الملغاة والبديلة), created_at
- **`invoice_items`**: نسخة مجمّدة (snapshot) من order_items وقت الاعتماد — id, invoice_id, product_name, quantity, unit_name, actual_price, line_total, is_available *(الفصل بين order_items وinvoice_items ضروري: الأول قابل للتحديث أثناء التنفيذ، والثاني مجمّد تمامًا بعد الاعتماد)*

### D.5 — المالية
- **`debts`**: id, customer_id, order_id (سبب الدين), amount, reason (`customer_cancellation`|`uncontactable`|`other`), applied_rate_snapshot (النسبة/القيمة وقت الإنشاء), status (`outstanding`|`settled`|`partially_settled`), created_at
- **`debt_settlements`**: id, debt_id, amount_paid, settled_by, settled_at, notes
- **`platform_settings`**: key, value (JSONB), updated_by, updated_at *(جدول Key-Value لكل الإعدادات القابلة للتغيير: رسوم التوصيل، نسبة العمولة، نسبة مديونية الإلغاء، ساعات العمل، نص التنبيه، رسالة الصيانة... — كل تغيير هنا يُسجَّل في Audit Log تلقائيًا عبر Trigger)*
- **`commission_ledger`**: id, order_id, completed_at, delivery_fee_at_time, commission_rate_applied, commission_amount, status (`due`|`paid`), created_at
- **`commission_payments`**: id, amount, period_from, period_to, paid_at, recorded_by, notes

### D.6 — التقييم والشكاوى
- **`ratings`**: id, order_id (unique — يمنع التكرار), customer_id, agent_id, stars (1-5), punctuality_score, behavior_score, order_accuracy_score, honesty_score, created_at
- **`complaints`**: id, customer_id, order_id (nullable), agent_id (nullable), type, details, status (`new`|`under_review`|`resolved`|`closed`), created_at, resolved_at, resolved_by

### D.7 — السياسات والموافقات
- **`policies`**: id, type (`terms`|`privacy`|...), version, content, published_at
- **`policy_consents`**: id, user_id, policy_id, consented_at, order_id (nullable — للربط بموافقة محددة وقت طلب معيّن)

### D.8 — Audit & Sessions
- **`audit_log`**: id, actor_id, actor_role, action, entity_type, entity_id, old_value (JSONB), new_value (JSONB), reason, created_at *(Append-only، لا UPDATE ولا DELETE مسموح به حتى على مستوى RLS)*
- **`user_sessions`**: id, user_id, device_info, ip_address, created_at, last_active_at, revoked_at, revoked_by

### D.9 — الفهارس المهمة (Indexes)
- `orders(customer_id, status)`, `orders(assigned_agent_id, status)` — لشاشات "طلباتي" و"طلباتي المسندة"
- `order_items(order_id)`, `invoice_items(invoice_id)`
- `debts(customer_id, status)` — لحساب الدين المستحق سريعًا عند إنشاء فاتورة جديدة
- `audit_log(entity_type, entity_id)` و `audit_log(created_at)` — للتقارير والفلترة الزمنية
- `product_price_history(product_id, recorded_at DESC)` — لجلب آخر سعر فعليًا

### D.10 — كيف نضمن عدم تغيّر البيانات التاريخية (القسم 57/63)
المبدأ: **كل رقم مالي يُستخدم في فاتورة يُنسخ (Snapshot) في لحظة الاعتماد**، ولا يُقرأ مباشرة من الإعداد الحي. تحديدًا:
- `delivery_fee_applied` في orders — نسخة، وليس قراءة من `platform_settings` كل مرة.
- `commission_rate_applied` في commission_ledger — نسخة.
- `applied_rate_snapshot` في debts — نسخة.
- `invoice_items` بالكامل منفصل عن `order_items` — الأول لا يتغير أبدًا بعد الاعتماد.

## E. Security & RLS Proposal

### E.1 مبدأ عام
كل جدول محمي بـ RLS **مفعّل افتراضيًا (Deny by default)**. لا صلاحية `SELECT`/`INSERT`/`UPDATE` بدون سياسة صريحة.

### E.2 أمثلة سياسات جوهرية (منطق، وليس كود جاهز مسبقًا لأن التنفيذ سيُبنى حسب الـ Schema أعلاه)
- **orders**: العميل يرى فقط `customer_id = auth.uid()`. المندوب يرى فقط `assigned_agent_id = auth.uid()` **بدءًا من لحظة تكليفه فعليًا بتنفيذ الشراء (مرحلة Shopping) وحتى اكتمال التوصيل** — تم تعديل هذا لاحقًا أثناء بناء دوال RPC ليعكس أن نفس المندوب هو من يشتري ثم يوصّل غالبًا (وليس فقط بعد Assigned كما ورد أولاً في هذا التقرير). لا يرى الطلب إطلاقًا أثناء المراجعة/القبول قبل أن يُختار. Business Admin وSuper Admin يريان الكل.
- **audit_log**: `SELECT` لـ Super Admin فقط. لا توجد سياسة `UPDATE`/`DELETE` على الإطلاق لأي دور (بما فيهم Super Admin عبر الواجهة — الحذف إن لزم يتم فقط عبر صلاحية قاعدة بيانات مباشرة خارج التطبيق، وهذا مقصود).
- **debts / commission_ledger / invoices**: القراءة حسب الدور، **الكتابة فقط عبر Edge Functions موقّعة بصلاحية Service Role** — لا INSERT/UPDATE مباشر من الواجهة حتى لو امتلك المستخدم صلاحية نظرية، لأن هذه العمليات تحتاج منطق حسابي (لا يجب الوثوق بالعميل لحساب إجمالي فاتورته).
- **agent_profiles**: المندوب يرى بيانات نفسه فقط ويعدّل `availability_status` الخاص به فقط.

### E.3 حماية العمليات المالية تحديدًا
اعتماد فاتورة، تسوية دين، تسجيل دفع عمولة، تغيير نسبة عمولة — **كل هذه عمليات RPC (Postgres Functions بـ SECURITY DEFINER)** تتحقق من الدور داخليًا وتُسجل في audit_log كجزء من نفس Transaction (بحيث يستحيل نجاح العملية دون تسجيلها).

### E.4 Session Management
- كل جلسة (`user_sessions`) تُنشأ عند تسجيل الدخول وتُربط بـ Supabase Auth session token.
- "إنهاء جلسة" من Super Admin = استدعاء `admin.deleteUser` session أو invalidate عبر Supabase Auth Admin API + تسجيل في audit_log.
- محاولات دخول فاشلة متكررة على نفس الرقم → قفل مؤقت (Rate limiting على مستوى Edge Function) لمنع Brute-force، خصوصًا أنه لا يوجد OTP كطبقة حماية إضافية حاليًا.

### E.5 حماية كلمات المرور
Supabase Auth يستخدم bcrypt/argon2 داخليًا — لا حاجة لتخزين يدوي، وهذا يحقق شرط "عدم تخزين نص واضح" تلقائيًا.

## F. WhatsApp — الحل المُحدَّث (بدون ميزانية): Prepared Manual Messages

بناءً على قرار عدم توفر ميزانية، تم إلغاء فكرة WhatsApp Cloud API المدفوع، والاعتماد بدلاً منها على **رسائل جاهزة يرسلها المندوب/الإداري يدويًا**، لكن بطريقة أكثر تنظيمًا من مجرد "زر يفتح واتساب فارغ":

**آلية العمل:**
1. عند وقوع حدث مهم (نفس قائمة القسم 42: قبول الطلب، الفاتورة جاهزة، في الطريق، تم التسليم... إلخ)، النظام **يُولّد تلقائيًا نص الرسالة كاملاً** من جدول `whatsapp_templates` (نفس الجدول المقترح سابقًا، قوالب قابلة للتعديل من لوحة التحكم) مع تعويض المتغيرات (اسم العميل، رقم الطلب، الإجمالي... إلخ).
2. تظهر في واجهة المندوب/الإداري بطاقة "رسالة جاهزة للإرسال" بجانب الطلب، مع **زر واحد** يفتح رابط Click-to-Chat:
   `https://wa.me/<رقم العميل>?text=<النص المُعدّ مسبقًا>`
   هذا يفتح واتساب (تطبيق أو ويب) مع النص جاهزًا بالكامل داخل خانة الكتابة — المستخدم فقط يضغط "إرسال". هذا مجاني 100% ولا يحتاج أي API أو تحقق من Meta.
3. عند الضغط على الزر، النظام يسجّل في `notification_log` أن الرسالة **تم تجهيزها/فتحها** (status = `prepared`)، مع العلم أنه لا توجد طريقة تقنية مجانية للتأكد من أن المستخدم ضغط "إرسال" فعليًا داخل واتساب نفسه — وهذا قيد معروف ومقبول في هذا الحل.
4. **فائدة إضافية:** بما أن الإرسال يمر عبر رقم واتساب المندوب/الإداري الشخصي أو التجاري العادي (وليس رقمًا مؤتمتًا)، العميل قد يرد مباشرة على نفس المحادثة، وهذا فعليًا يحسّن تجربة الدعم مقارنة بإشعار آلي بلا رد.

**الأثر على التصميم:**
- لا حاجة لـ Edge Function خاصة بإرسال WhatsApp، ولا حساب Meta Business، ولا تكلفة شهرية.
- جدول `whatsapp_templates` و`notification_log` يبقيان كما هما في التصميم لأنهما مفيدان لتتبّع أي الرسائل جُهّزت ومتى، ويسهّلان الترقية لاحقًا لـ Cloud API الرسمي إذا توفرت ميزانية مستقبلاً (فقط نُبدّل طبقة "الإرسال" دون تغيير الـ Schema).
- **قيد يجب توضيحه للإدارة:** هذا الحل يعتمد على وجود شخص (مندوب/إداري) متصل وجاهز للضغط على الزر عند كل حدث؛ لا يعمل تلقائيًا في حال غياب الشخص عن الجهاز، على عكس الحل الآلي بالكامل. هذا مقبول حاليًا لأن حجم التشغيل صغير (شخص واحد أساسًا).

## G. Notification Architecture (Push)

- Push مبني بالكامل على Web Push (VAPID keys) — مجاني، لا مزوّد خارجي مطلوب.
- جدول `push_subscriptions` (user_id, endpoint, keys, created_at).
- نفس مبدأ WhatsApp: حدث → Trigger → Edge Function → إرسال + تسجيل في `notification_log`، وفشل الإرسال لا يكسر أي عملية عمل.
- القائمة المرسلة تلتزم حرفيًا بقائمة القسم 42 فقط — لا إشعار عند كل UPDATE بسيط.

## H. Complete Order State Machine

```
NEW_ORDER → REVIEW (تلقائي عند الإرسال، لا فعل بشري)
REVIEW → ACCEPTED           [فعل: Business Admin يقبل]
REVIEW → REJECTED            [فعل: Business Admin يرفض + سبب] → نهائي
ACCEPTED → SHOPPING           (تلقائي عند القبول)
SHOPPING → INVOICE_PREPARATION [فعل: المندوب ينهي تسجيل كل الأصناف]
INVOICE_PREPARATION → INVOICE_APPROVED [فعل: Business/Super Admin يعتمد]
INVOICE_APPROVED → READY_FOR_DELIVERY (تلقائي عند الاعتماد)
READY_FOR_DELIVERY → ASSIGNED  (تلقائي عبر Assignment Service)
ASSIGNED → ON_THE_WAY          [فعل: المندوب يبدأ التوصيل]
ON_THE_WAY → DELIVERED         [فعل: المندوب يضغط "تم التسليم" — يتطلب تأكيد استلام المبلغ]

مسارات الإلغاء (يمكن أن تحدث من أي حالة قبل DELIVERED):
{NEW_ORDER, REVIEW} → CANCELED_BY_CUSTOMER   (لا مديونية أبدًا)
{ACCEPTED..ON_THE_WAY} → CANCELED_BY_CUSTOMER (مديونية محتملة — القسم 33)
أي حالة قبل DELIVERED → CANCELED_BY_BUSINESS  [يتطلب سبب؛ مديونية فقط إذا السبب = uncontactable]

مسار خاص أثناء التنفيذ:
ASSIGNED/ON_THE_WAY → (المندوب يعجز عن الإكمال + سبب) → READY_FOR_DELIVERY (يعود لنظام التعيين تلقائيًا، سجل transfer يُنشأ داخليًا فقط)

مسار تصحيح الفاتورة:
INVOICE_APPROVED (خطأ مكتشف) → invoice.status=CANCELED (فاتورة جديدة تُنشأ، والطلب نفسه يبقى في READY_FOR_DELIVERY أو أبعد حسب توقيت الاكتشاف)
```

**قاعدة صارمة:** لا يوجد أي زر "تغيير حالة يدوي عام" في أي لوحة تحكم. كل انتقال أعلاه مرتبط حصرًا بفعل محدد كما هو موضح بين الأقواس.

## J. Edge Cases — كيف يتعامل التصميم معها

| الحالة | المعالجة |
|---|---|
| العميل يلغي قبل القبول | إلغاء فوري، لا دين، الطلب → CANCELED_BY_CUSTOMER |
| العميل يلغي بعد القبول | دين محتمل حسب إعداد لوحة التحكم، يُنسخ المعدل وقت الإنشاء في `debts.applied_rate_snapshot` |
| كل المنتجات غير متوفرة | الفاتورة تُحسب بإجمالي = رسوم التوصيل فقط (+ دين سابق إن وجد)؛ يُسمح بذلك، لا حد أدنى للطلب |
| المندوب يعجز عن الإكمال | يسجل سببًا إلزاميًا → `order_transfers` → عودة تلقائية لـ READY_FOR_DELIVERY → إعادة تعيين |
| لا يوجد مندوب متاح | الطلب يبقى في READY_FOR_DELIVERY كـ "قيد الانتظار"، Business Admin يُنبَّه عبر Dashboard (وليس Push للعميل بشكل متكرر) |
| العميل لديه دين | يُضاف تلقائيًا لأي فاتورة جديدة عبر قراءة `debts` عند إنشاء `invoice` — لا يمنع الطلب ما لم يُفعَّل ذلك مستقبلًا من الإعدادات |
| تصحيح فاتورة | إلغاء القديمة (status=CANCELED + سبب) وربطها بالجديدة عبر `superseded_by_invoice_id`، القديمة تبقى في السجل |
| فشل WhatsApp/Push | يُسجَّل في `notification_log`، لا يوقف أي انتقال حالة، تتم إعادة محاولة لاحقًا |
| تغيير رسوم التوصيل/العمولة | يُحدَّث `platform_settings` فقط؛ الطلبات القائمة تحتفظ بالقيم المنسوخة مسبقًا في `orders`/`commission_ledger` |
| تغيير بيانات العميل بعد إنشاء الطلب | لا يؤثر — العنوان منسوخ في `delivery_address_snapshot` وقت الإنشاء |

## L. Testing Strategy (مقترح)
1. **Unit tests** على منطق حساب الفاتورة والعمولة والدين (أكثر الأجزاء حساسية ماليًا).
2. **State machine tests**: التأكد من استحالة الوصول لأي انتقال غير مسموح به (اختبار كل حافة في الرسم البياني بالقسم H).
3. **RLS tests**: لكل جدول حساس، اختبار محاولة وصول من كل دور والتأكد من الرفض المتوقع.
4. **Idempotency tests** لعمليات Webhook/WhatsApp (تجنب إرسال مكرر عند إعادة المحاولة).
5. **E2E** لسيناريو كامل: تسجيل → طلب → قبول → شراء → اعتماد فاتورة → تسليم → تقييم.

## M. Deployment Strategy (مقترح)
- بيئتان: Staging (Supabase project منفصل) وProduction.
- Migrations عبر Supabase CLI مُصدَّرة بملفات SQL في Git (لا تعديل يدوي على قاعدة الإنتاج مباشرة).
- Frontend: Vercel مع Preview Deployments لكل Pull Request.
- Secrets (WhatsApp tokens، VAPID keys) في Environment Variables فقط، أبدًا في الكود.
